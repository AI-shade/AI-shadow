# 안심앨범 (Anshim Album)

아이 사진을 SNS에 올리기 전에 위험 요소(배경 텍스트·위치정보·스케줄 패턴 노출 등)를
자동으로 진단하고, 얼굴을 보호한 채로 보정까지 해주는 웹 앱입니다. Campus AX-Ton
프로젝트로 진행했고, 이 문서는 프론트/백엔드 목업에서 시작해 단계별로 실제 기능
(OCR, 얼굴 분석, Claude API 위험도 진단, 스케줄 패턴 분석, 이미지 보정)을 하나씩
붙여온 전체 개발 기록입니다.

## 1. 프로젝트 구조 및 빠른 시작

### 파일 구조
```
child/
├── index.html          # 프론트엔드 전체 (별도 빌드 없음, 순수 HTML/CSS/JS 한 파일)
├── server/              # Claude Vision·위험도진단·fal.ai를 중계하는 Express 백엔드
│   ├── server.js         # 전체 API 엔드포인트
│   ├── .env              # 실제 API 키 (gitignore 대상 — 직접 만들어야 함, 아래 참고)
│   ├── .env.example       # .env 템플릿 (플레이스홀더만 있음, 이 파일은 커밋됨)
│   └── package.json
├── test/
│   ├── regression.js      # 회귀 테스트 5케이스 (Playwright)
│   ├── fixtures/           # 테스트용 합성 이미지
│   └── correction-samples/ # 2단계 보정 방식별 검증 결과 이미지
├── scripts/
│   └── check-secrets.sh   # 커밋 전에 돌려보는 API 키 유출 점검 스크립트
├── files/                 # 기획서·프롬프트 문서 (아이사진_SNS위험진단_*.md)
└── docs/superpowers/specs/ # 설계 문서
```

**왜 백엔드가 필요한가**: Claude API 키가 브라우저에 노출되면 안 되므로, 프론트는
직접 Claude를 호출하지 않고 항상 `server/`의 Express 백엔드를 거칩니다. 얼굴은
항상 이 백엔드로 보내기 전에 브라우저에서 마스킹됩니다(예외: fal.ai 배경교체 — 아래
"구현된 기능" 참고).

### 설치 및 실행

서버 **두 개**를 띄워야 합니다 — 정적 프론트와 백엔드.

```bash
# 1) 프론트 (이 폴더 child에서)
python -m http.server 8000

# 2) 백엔드 (server/ 폴더에서, 최초 1회 npm install 필요)
cd server
npm install
cp .env.example .env
# .env 파일을 열어서 실제 키 값으로 채운 뒤 저장 (아래 "환경변수" 참고)
npm start
```

브라우저에서 `http://localhost:8000/index.html` 접속. (`file://`로 직접 열면 CORS
문제로 Tesseract.js가 canvas 데이터를 못 읽어 실패할 수 있으니 항상 로컬 서버로.)

**백엔드 없이 프론트만 띄우면?** Claude Vision 호출이 자동으로 실패하고 Tesseract로
전환되어 동작은 합니다 (아래 7번 항목 "자동 폴백" 참고) — 다만 그러면 이번 단계까지의
개선 효과를 못 보는 것이니, 가능하면 백엔드도 같이 띄워주세요.

### 필요한 환경변수 (`server/.env`)

| 변수 | 필수 여부 | 용도 | 없으면 |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | **필수** | OCR/위험도진단/캡션제안/스케줄분석 등 거의 모든 기능 | 서버가 시작 시 경고를 띄우고, 관련 기능이 전부 Tesseract/규칙기반 폴백으로만 동작 |
| `FAL_KEY` | 선택 | 2단계 보정의 "AI 배경 교체"(fal.ai flux-kontext-pro) 기능에만 필요 | 해당 기능만 "준비 중"으로 비활성화되고, 나머지 기능은 정상 동작 |
| `PORT` | 선택 (기본 3001) | 백엔드 포트 | 3001 사용 |

`.env.example`을 복사해서 `.env`를 만들고 실제 값으로 채우세요. **`.env.example`에는
절대 실제 키를 넣지 마세요** — 그건 커밋되는 템플릿 파일이고, 실제 키는 `.env`(gitignore
대상)에만 있어야 합니다.

### 구현된 기능 / 아직 미구현

**실제로 동작하는 것** (전부 실사진으로 검증 완료, 아래 각 섹션에 근거 기록):
- 얼굴 검출(face-api.js) + 배경 텍스트 OCR(Claude Vision, 실패 시 Tesseract 자동 폴백)
- 위험도 점수/등급 산출 + 캡션 제안 (Claude API, 8·9번 섹션)
- 과거 게시물 스크린샷 기반 스케줄 패턴 분석 (요일·시간·장소 반복 탐지, 11번 섹션)
- 2단계 보정: 스마트 크롭 / 배경 흐림 / 스티커 덮기 (Canvas, 무료, 12번 섹션) +

- 얼굴 검출 실패 시 안전장치 (프라이버시 우선 확인 모달, 14번 섹션)

**아직 없는 것**:
- 처리된 이미지를 1단계 파이프라인에 다시 통과시켜 재검증하는 "3단계 검증" 기능
  (위험 해결 여부·신규 위험·인물 보존 확인) — 다음 작업 예정
- 사용자가 직접 얼굴 위치를 지정하는 수동 마스킹 UI (14번 섹션 "남은 과제" 참고)

### 알려진 이슈 (우선순위 순, 상세 근거는 해당 섹션 참고)

1. ~~얼굴 검출 실패 시 마스킹 미적용~~ — **수정 완료** (14번 섹션). 얼굴 0개 감지 시
   자동으로 외부 전송을 멈추고 사용자 확인을 먼저 받도록 변경함.
2. **스티커/크롭 위치 정확도** — 2단계 보정은 위치 계산에 Tesseract를 다시 쓰는데,
   Tesseract가 실제 사진에서 전화번호·번지수 같은 작은 텍스트는 못 찾는 경우가 많음
   (12번 섹션). 못 찾은 텍스트는 크롭/스티커로 처리가 안 됨.
3. **flux 배경교체의 구도 재구성 문제** — 합성 사진에서는 flux-kontext-pro가 전체
   구도를 재구성해버리는 문제를 발견했으나, 실제 촬영 사진으로 재검증한 결과 실제
   사진에서는 구도가 잘 유지됨을 확인함 (13번 섹션). 다만 출력 해상도가 원본과
   ~4% 다르게 나오는 사소한 차이는 남아있음.
4. **"안전 우선" 선택 시 텍스트 판독 품질 저하** — 얼굴 미검출로 로컬 Tesseract만 쓰게
   되면 판독 정확도가 Claude Vision보다 크게 떨어짐 (14번 섹션). 근본적으로는
   트레이드오프이며 완전히 해결하기보다 사용자가 인지하고 선택하도록 설계함.

## 2. 기본 사용

1. "사진" 항목에 사진을 업로드 (사람 얼굴, 간판·표지판 등)
2. 캡션 등 나머지 항목은 자유롭게 입력 (선택)
3. "위험도 진단하기" 클릭 → 실제로 face-api.js(얼굴 분석)와 Tesseract.js(OCR)가 브라우저에서 실행됨
4. 결과 화면 사진 위에 실제 감지 위치에 핀이 찍힘 — **초록 핀은 얼굴(face-api.js)**, **금색 핀은 텍스트(Tesseract.js)**

**첫 실행 시 주의**: `kor+eng` 언어팩, face-api.js 모델 가중치를 CDN에서 처음 내려받기 때문에
수십 초 정도 더 걸릴 수 있습니다. 인터넷 연결이 필요합니다. 두 번째 실행부터는 브라우저 캐시
덕분에 빨라집니다. 얼굴 모델은 페이지가 열리자마자 백그라운드에서 미리 준비(워밍업)해두므로,
폼을 입력하는 동안 이 비용이 대부분 숨겨집니다 (7번 항목 참고).

## 3. 디버그 모드 (실제 사진 검증용)

URL 뒤에 `?debug=1`을 붙여서 접속하면:

```
http://localhost:8000/index.html?debug=1
```

- 진단 결과 화면 맨 아래에 **"🔧 얼굴 분석 디버그 정보"** + **"🔧 OCR 디버그 정보"** 패널이 나타남
  - 얼굴: 검출된 얼굴별 신뢰도, 크기(프레임 대비 %), roll(기울기)/yaw(근사 좌우돌림), 좌표(%) 표 + 단계별 소요시간
  - OCR: 원본 vs 전처리(흑백+대비강화) 이미지 비교, 전처리 전/후 OCR 텍스트 비교, 줄 단위 1차/2차 결과·신뢰도·좌표 표, 단계별 소요시간
- 브라우저 콘솔(F12 → Console)에도 동일한 내용이 더 상세히 로그로 찍힘 (`[FACE]`, `[OCR]`, `[OCR][debug]`, `[FACE][debug]` 태그)

콘솔에서 직접 확인하고 싶다면 개발자도구를 열고 사진을 업로드 → 진단하기를 눌러보세요.
`[FACE] 처리 완료 — 총 XXXXms`, `[OCR] 처리 완료 — 총 XXXXms` 로그에 요약이 찍힙니다.

## 6. 확인된 한계 (정직하게 밝힐 것 — 발표 자료용)

**기준 테스트 케이스**: 야간 네온 간판 실사진("꽃집 누아블룸", 960×540, 카카오톡 압축 거침).
포함된 텍스트: "꽃집 누아블룸"(대형 분홍+흰색 네온), "010-4956-6091"(전화번호),
"1118-1"(번지수), "아인종합기획"(좌측 하단 작은 로고).

### 발견 → 수정한 문제
- **최초 상태: 이 사진에서 텍스트 0개 감지.** 원인은 Tesseract 페이지 분할 모드
  (PSM)를 `SINGLE_COLUMN` 하나로 고정해둔 것 — 이 사진처럼 큰 글씨+흩어진 작은 글씨가
  섞인 레이아웃에서는 후보를 아예 찾지 못함. `SINGLE_COLUMN`과 `SINGLE_BLOCK` 두 모드를
  같이 돌려서 합치는 방식으로 바꿈.
- 분홍색 네온처럼 채도 높은 색은 표준 휘도 공식으로 그레이스케일 변환하면 어두운
  배경과 대비가 거의 사라짐(실측: RGB(255,29,160)가 밝기 111로 떨어짐). max(R,G,B)
  방식으로 바꿔서 색 있는 네온도 흰색 텍스트와 동등하게 보존되도록 수정.
- 저신뢰도 잡음 라인(신뢰도 60% 미만, 특수문자만 있는 줄, 2글자 미만, 중복 텍스트)을
  걸러내는 필터를 추가함.

### 그래도 남아있는 한계
- **대형 간판 텍스트는 부분적으로만 인식됨**: "꽃집 누아블룸" → "교지 누아블룸"으로 인식
  (완전히 정확하지 않지만 어느 정도 단서는 됨)
- **전화번호("010-4956-6091"), 번지수("1118-1"), 작은 로고("아인종합기획")는
  최종 결과에서 검출되지 않음** — 1차 스캔에서 후보로 아예 안 잡혀서 2차 확대 재인식 단계까지
  가지도 못함. PSM을 하나 더(SPARSE_TEXT) 추가하면 이 중 일부는 잡히는 걸 확인했지만,
  결과가 실행할 때마다 들쭉날쭉하고(비결정적) 처리시간이 더 늘어나서 이번 단계에는 포함하지 않음
- **처리시간 증가**: 이 사진 기준 약 4.4~4.6초 (PSM을 두 번 돌리고 2배 확대까지 하는 비용).
  기존(PSM 1개, 확대 없음) 대비 느려졌지만 사용자가 기다릴 만한 수준으로 판단됨
- 종합하면: "완벽한 판독이 아니라 위치 특정 가능한 단서 존재 여부 판단"이라는 원래 설계
  목표에는 부합하지만(큰 간판 텍스트는 대략 알아볼 수준으로 나옴), 사진 하나에 있는
  모든 텍스트를 다 잡아내지는 못하는 상태입니다

## 7. 얼굴 분석(face-api.js) 검증 결과 — B단계

**모델**: tinyFaceDetector(검출) + faceLandmark68Net(랜드마크, 각도 계산용). 두 모델 다
face-api.js 공식 저장소 가중치를 CDN(jsdelivr)으로 바로 불러와서 씀.

**설정 튜닝**: 기본값(`inputSize: 416, scoreThreshold: 0.5`)은 인물이 화면 전체를 채우지
않는 일반적인 스냅샷에서 얼굴을 놓치는 경우가 있었음 (실측: 실제 얼굴의 신뢰도가 46~47%로
기본 임계값 미달). `inputSize: 608, scoreThreshold: 0.3`으로 바꿔서 오탐(얼굴 없는 사진에서
잘못 검출) 없이 더 잘 잡도록 조정함 — 텍스트만 있는 사진(꽃집간판.jpg)으로 오탐 없음을 확인.

### 테스트한 5가지 케이스 (모두 통과)
| 케이스 | 결과 |
|---|---|
| 텍스트만 (얼굴 없음) | 얼굴 0개로 정상 처리, 에러 없음, 텍스트 핀은 정상 표시 |
| 얼굴만 (단독 인물사진) | 얼굴 1개 정상 검출 (신뢰도 77%) |
| 얼굴+텍스트 결합 | 얼굴 핀(초록)·텍스트 핀(금색)이 겹치지 않고 각자 정상 위치에 표시 |
| 여러 명(6명) | 6명 전원 정상 검출, roll/yaw/신뢰도 각각 다르게 정상 산출 |
| 작은 배경 얼굴 (프레임의 약 5%) | **0개 — 감지 실패** (아래 한계 참고) |

### 확인된 한계
- **아이 얼굴 테스트 데이터 없음**: face-api.js 공식 예제/테스트 저장소를 뒤져봤지만 전부
  성인(Big Bang Theory 출연진) 사진뿐이고 아이 얼굴 샘플이 없었음. 인터넷에서 실제 아이
  사진을 구해다 테스트하는 것은 이 서비스가 막으려는 것과 같은 종류의 프라이버시 문제라
  판단해 시도하지 않음. **따라서 아이 얼굴 인식률은 이번 단계에서 실측하지 못했고, 검증되지
  않은 상태**임 — face-api.js 모델이 주로 성인 얼굴 위주 데이터셋(WIDER FACE 등)으로
  학습된 것으로 알려져 있어 아이 얼굴에서 정확도가 떨어질 가능성이 있음. 실제 서비스
  적용 전 아이 얼굴 사진으로 별도 검증이 반드시 필요함
- **작은 배경 얼굴은 감지 안 됨**: 프레임의 약 5% 너비(예: 1400px 폭 사진에서 70px 얼굴)
  수준의 작은 얼굴은 `inputSize`를 늘려도 검출 실패. 기획서상 "함께 나온 사람"도 위험
  요소인데, 배경에 작게 찍힌 사람은 놓칠 수 있음 — 정면 큰 얼굴 위주로만 잡힌다고
  보수적으로 가정해야 함
- **yaw(좌우 돌림)는 근사치**: 실제 3D 머리 자세 추정(PnP 등)이 아니라, 코가 양쪽 눈 대비
  얼마나 비대칭 위치에 있는지로 추정한 값. 정확한 각도라기보다 "많이 돌아갔는지 아닌지"
  정도의 참고값으로만 취급해야 함. roll(기울기)은 눈 위치 기반이라 상대적으로 정확함

### 처리 시간
- **얼굴 검출 자체의 첫 실행 비용**: tfjs가 WebGL 셰이더를 최초 컴파일하는 데 실측
  2~3.5초가 걸림 (이후 호출은 0.5초대로 줄어듦) — tfjs의 잘 알려진 특성
- 이 비용을 사용자가 "위험도 진단하기"를 누르는 순간이 아니라 **페이지가 열리자마자
  백그라운드에서 미리 치르도록(워밍업) 구현**함
- **실측 결과**:
  - 폼 입력 없이 사진 올리자마자 바로 제출(최악의 경우): 얼굴+OCR 합산 총
    **8.4~9.6초**
  - 실제로 폼을 입력하는 정도의 시간(약 4초)을 두고 제출(현실적인 경우): 총
    **2.6~5.2초**로 감소
- 결론: 워밍업 덕분에 일반적인 사용 흐름에서는 기다릴 만한 수준. 다만 사진을 올리자마자
  바로 버튼을 누르는 극단적으로 빠른 사용자에게는 여전히 8초 이상 걸릴 수 있음

## 8. Claude Vision 전환 결과 — C단계

Tesseract가 실사진에서 계속 오독하는 문제(6번 항목)를 해결하려고 텍스트 판독을
Claude Vision(`claude-haiku-4-5`)으로 교체했다. 아키텍처는
`docs/superpowers/specs/2026-08-19-claude-vision-ocr-design.md` 참고.

### 동작 방식
- **평소**: Claude Vision만 호출. 실패(네트워크 끊김, 키 오류, 응답 파싱 실패 등) 시
  **자동으로 Tesseract 결과로 전환** — 사용자에게 에러 없이 정상 진행됨 (실측: 백엔드를
  강제로 끄고 테스트, 에러 팝업 없이 Tesseract 결과로 자연스럽게 전환되는 것 확인)
- **`?debug=1`**: 항상 Claude Vision + Tesseract 둘 다 실행해서 비교표로 보여줌
  (인식 텍스트, 개수, 신뢰도, 처리시간 — Claude는 신뢰도 개념이 없어 "제공 안 됨"으로 표시)
  + 콘솔에 `[비교]` 태그로 같은 데이터를 구조화해서 로그(여러 사진 테스트하며 발표자료용
  데이터를 모을 수 있게)

### 프라이버시: 얼굴 마스킹 검증
face-api로 검출한 얼굴 bbox에 20% 패딩을 주고 완전 불투명 검은 사각형으로 덮은 뒤에만
Claude Vision으로 전송함. `?debug=1` 디버그 패널에서 **실제로 전송된 마스킹 이미지를
직접 확인 가능** — `test/fixtures/face-plus-text.jpg`(얼굴+간판 합성 사진)로 테스트한
결과, 얼굴이 검은 사각형으로 정상적으로 가려진 채 전송되는 것을 확인했다.

### `꽃집간판.jpg` 기준 정확도 비교 (같은 사진, 실측)

| 목표 텍스트 | Tesseract (기존) | Claude Vision (신규) |
|---|---|---|
| 꽃집 누아블룸 | "교지 누아블룸" (오독) | 대부분 정확히 읽음, 가끔 "누아블롱"처럼 미세하게 틀림 (아래 참고) |
| 010-4956-6091 | 미검출 | **정확히 읽음** |
| 1118-1 | 미검출 | **정확히 읽음** (단, 같은 값이 위치만 다르게 중복 검출되는 경우 있음) |
| 아인종합기획 | 미검출 | 부분적으로 읽음 ("아인 종로기획", "아인종기원" 등 호출마다 다르게 오독) |

**Claude Vision이 Tesseract보다 확실히 나은 점**: 전화번호·번지수처럼 Tesseract가
아예 놓쳤던 항목을 잡아냄. **여전히 남는 한계**: 작은 로고 텍스트("아인종합기획")는
여전히 부정확하고, **같은 사진을 여러 번 호출해도 결과가 조금씩 달라짐**(비결정적) —
"교지 누아블룸" 같은 완전 오독은 없어졌지만 "누아블룸"/"누아블롱"처럼 미세한 편차는
호출마다 발생할 수 있음. 발표 자료에는 "매번 100% 동일한 결과가 아니라는 점"을 함께
밝히는 게 좋다.

### 좌표 정밀도 트레이드오프 (합의된 사항)
Claude Vision은 픽셀 좌표를 주지 않고 "상단 중앙" 같은 텍스트로만 위치를 알려줌.
9분할 그리드로 근사 변환해서 핀을 찍기 때문에, Tesseract 때처럼 정확한 글자 위치가
아니라 **대략적인 구역**만 표시된다 (예: 핀이 실제 글자보다 조금 벗어난 위치에 찍힐 수 있음).

### 비용 (실측)
- `꽃집간판.jpg` 1장당: 입력 약 938 토큰, 출력 약 329 토큰
- `claude-haiku-4-5` 요금(입력 $1/1M, 출력 $5/1M) 기준 **장당 약 $0.0026** (3원 미만)
- 기획서에 있는 flux-kontext-pro 비용(장당 $0.04~0.055)과 비교해도 매우 저렴한 수준

### 처리 시간 (실측)
- Claude Vision 백엔드 왕복: 약 2.6~4.1초 (얼굴 분석·업로드 폼 입력과 겹쳐서 체감시간은 이보다 짧음)
- 자동 폴백이 발생하는 경우(백엔드 다운 등): Claude 요청 타임아웃까지 기다린 뒤 Tesseract를
  처음부터 다시 돌리므로 전체 **10초 이상** 걸릴 수 있음 — 흔치 않은 경로지만 발표 중
  네트워크가 실제로 끊기면 이 정도 지연은 각오해야 함

### 회귀 테스트 갱신
`test/regression.js`에 Claude Vision 비교표 검증 케이스를 추가했다. Claude 응답이
비결정적이라 텍스트 어서션은 부분 문자열(예: "누아블")로 느슨하게 잡았다. 이 스크립트를
돌릴 때마다 Claude Vision이 실제로 호출되어 소액 비용이 발생한다는 점 참고.

## 9. 위험도 진단 + 캡션 제안 Claude API 연동 — D단계

`buildMockDiagnosis()`(규칙 기반)를 실제 Claude API 호출로 교체. `server/`에
`POST /api/diagnose-risk`, `POST /api/suggest-captions` 두 엔드포인트를 추가했다
(프롬프트 문서 1번·6번 그대로 사용, 이미지는 보내지 않고 텍스트 데이터만 전송).
스케줄 유출 관련 UI는 이번에도 범위 밖이라 기존 규칙 기반 로직을 그대로 유지했다.

### `꽃집간판.jpg` 기준 3회 반복 호출 결과 (요청하신 표)

| 회차 | 종합점수 | 등급 | 위치노출점수 | 권장조치 개수 | 처리시간 |
|---|---|---|---|---|---|
| 1회 | 78 | 상 | 85 | 5 | 15.0초 |
| 2회 | 78 | 상 | 82 | 6 | 14.3초 |
| 3회 | 72 | 상 | 78 | 6 | 15.9초 |

**점수 편차: 6점(72~78)** — 예시로 걱정하신 "80→55→92" 같은 큰 편차는 없었다.
등급이 전부 "상"으로 안정적인 것도 확인. (참고: 첫 번째 실험 라운드에서는 **같은
72점인데 등급이 "중"/"상"으로 갈리는 진짜 비일관성**을 발견했음 — 이건 프롬프트
문제라기보다 "Claude가 점수와 등급 라벨을 각각 독립적으로 생성"하는 구조적 문제라,
프롬프트를 다듬는 대신 **등급을 점수 기준으로 클라이언트에서 확정**하도록 고쳐서
근본적으로 없앴다 (70점↑ 상 / 45점↑ 중 / 그 외 하 — 기존 mock 로직과 동일한 경계값).
점수 자체(6점 편차)는 여전히 Claude의 판단 편차이며, 더 줄이려면 프롬프트에 채점
기준 예시를 추가하는 게 다음 개선 후보다.

### 처리 시간
- 위험도 진단 호출 자체가 약 7~10초로 가장 오래 걸림 (자연어 설명이 길어서 출력
  토큰이 700개 이상 나옴)
- 캡션 제안은 위험도 진단과 서로 독립적이라 **병렬로 실행**하도록 구현 (순차 실행 시
  16~20초 → 병렬 적용 후 14~16초)
- 전체 파이프라인(얼굴분석 → 텍스트판독 → 위험도진단+캡션제안 병렬) 총합 **약
  14~16초** — OCR/얼굴분석만 하던 이전 단계(2~5초)보다 확연히 느려짐. 발표 데모
  때는 이 정도 대기시간을 감안해야 한다

### 비용 (실측, 사진 1장 진단 기준)
- Claude Vision(텍스트판독) + 위험도진단 + 캡션제안 3개 호출 합산 약 **$0.0095**
  (13원 미만)
- `claude-haiku-4-5` 기준이라 매우 저렴하지만, 위험도진단 호출 하나가 전체 비용의
  절반 가까이 차지함 (출력 토큰이 김)

### 자동 폴백 검증
백엔드를 완전히 꺼서 Claude Vision·위험도진단·캡션제안 3개 호출이 전부 실패하는
상황을 재현 — 에러 팝업 없이 Tesseract 결과 + 기존 규칙 기반 `buildMockDiagnosis()`로
자연스럽게 전환되는 것을 확인했다 (콘솔에는 각 실패 사유가 로그로 남음).

### 회귀 테스트
`test/regression.js` 3케이스 모두 통과 (얼굴/텍스트 핀 개수는 이번 단계에서 건드리지
않아 영향 없음 확인).

## 10. 체감 속도 개선 — #1 출력 토큰 제약 + #3 단계별 표시 + #4 로딩 UX

D단계에서 처리시간이 14~16초로 길어져서, 실제 시간 단축(#1)과 체감 속도 개선(#3, #4)을
같이 적용했다. 스트리밍(#2)은 검토 후 제외했다 — 응답이 JSON 구조라 부분 파싱이
까다롭고, 실제 총 대기시간은 줄이지 못해 #3과 효과가 크게 겹친다고 판단했다.

### #1 출력 토큰 제약 (실측 실험 후 적용)
위험도 진단 프롬프트에 "위치노출근거 2문장 이내", "종합설명 3문장 이내", "권장조치
최대 3개" 제약을 추가. 동일 입력으로 6회 호출(기존 3회, 제약 3회) 비교:

| | 평균 출력 토큰 | 평균 응답시간 |
|---|---|---|
| 기존 | 782 토큰 | 7.07초 |
| 제약 적용 | 519 토큰 (−34%) | 5.23초 (−26%) |

내용을 직접 다 읽고 비교했을 때 품질 저하는 없었음 — 오히려 기존 5~6개짜리 권장조치는
표현만 다르게 반복되는 항목이 있었는데, 3개로 줄이니 더 핵심만 남았다.

### #3 단계별 표시 (구현 완료)
얼굴+텍스트 판독이 끝나는 즉시(위험도 진단을 기다리지 않고) 결과 화면으로 전환한다.
사진과 핀(얼굴/텍스트)은 이 시점에 이미 실제 값이고, 점수 게이지·위치노출 근거·권장
조치·종합설명·캡션 제안 자리는 스켈레톤(회색 펄스 바)으로 채워뒀다가 위험도 진단이
끝나면 실제 값으로 교체한다.

**실측 (`꽃집간판.jpg`, 폼 입력 시간 확보한 현실적 조건)**

| 구간 | 시간 |
|---|---|
| 결과 화면 전환까지 (목표 4~6초) | **3.2~3.6초** ✅ 목표 이내 |
| 전환 후 스켈레톤이 채워지기까지 | 5.6~6.5초 |
| 전체 (클릭 ~ 완전히 채워짐) | 8.8~10.1초 |

이전 단계(#1 적용 전 14~16초, #1만 적용 시 11.2~11.7초)와 비교하면 **총 대기시간
자체는 #1의 효과**고, #3은 "3초대에 뭔가 화면에 뜬다"는 체감 개선을 더한 것 — 사진과
감지된 텍스트를 먼저 보여주는 것만으로도 훨씬 덜 멈춰있는 느낌을 준다.

### #4 로딩 UX (구현 완료)
- 스켈레톤 위에 회전 문구를 1.4초 간격으로 표시: "체크리스트 정보 종합 중…" →
  "위치·상황 정보 분석 중…" → "위험 요소 판단 중…" → "권장 조치 작성 중…"
- **정직하게 밝힐 점**: 이 문구들은 실제 백엔드 진행 상황과 연동된 게 아니라 **고정된
  타이머로 도는 근사치**다. Claude API 호출 하나가 통짜로 진행되기 때문에(스트리밍을
  안 쓰기로 했으므로) "지금 정확히 몇 번째 단계를 처리 중인지"는 알 방법이 없다.
  실측해보니 4개 문구가 5.6~6.5초 동안 자연스럽게 다 순환되긴 하지만, 이건 우연히
  타이밍이 맞은 것이지 실제 진행 상태를 반영한 게 아니다
- 기존 "분석 중" 화면의 스텝 표시(얼굴 분석 → 텍스트 감지 → [과거 게시물])는 실제
  진행 순서와 정확히 일치함 — 이 부분은 원래도 정확했음. 다만 기존에 있던 "위험도
  종합 판단 중" 스텝은 이제 결과 화면으로 넘어간 뒤에 처리되므로 분석 중 화면에서는
  제거하고, 대신 "사진 분석이 끝나는 대로 먼저 결과 화면을 보여드려요" 안내 문구를 추가함

### 회귀 테스트 (구조 변경으로 수정 필요했음)
`test/regression.js`가 기존엔 "결과 화면이 뜨면 바로 검증"했는데, 이제 결과 화면이
스켈레톤 상태로 먼저 뜨기 때문에 그 시점에 검증하면 실패한다 (실제 버그 아니고
테스트가 새 구조를 못 따라간 것). 스켈레톤이 다 채워질 때까지 기다리도록
`page.waitForFunction(...)`을 추가해서 고쳤고, 재실행 결과 3케이스 모두 통과.

## 11. 스케줄 패턴 분석 — 핵심 차별점 구현

과거 게시물 스크린샷 업로드는 있었지만 `pastCount`만 세던 목업 상태를 실제 분석으로
교체. 프롬프트 문서 2번을 그대로 사용했다.

### 구현
- `server/`에 `POST /api/analyze-screenshot`(스크린샷 1장 → 캡션/게시시점/배경텍스트
  추출), `POST /api/analyze-schedule-pattern`(N개 게시물 정보 → 패턴 분석) 두 엔드포인트 추가
- **스크린샷도 얼굴 마스킹 적용** — 다른 이미지와 동일한 프라이버시 원칙. face-api로
  검출 후 마스킹된 이미지만 Claude Vision에 전송
- 스크린샷 N장은 서로 독립적이라 **병렬 처리**(`Promise.all`) — 한 장 실패해도 나머지에
  영향 없음. "한 메시지에 이미지 여러 장"도 API 자체는 지원하지만, 실패 시 격리가 안
  되고 비용도 이미지 토큰 총량은 어차피 비슷해서 절약 효과가 적어 **병렬 개별 호출을
  채택**함
- 결과 화면에 "발견된 패턴"(근거 게시물 번호 포함), "예측 가능해지는 정보" 항목 신규
  추가. 위험도진단·캡션제안과 마찬가지로 단계별 표시(스켈레톤) 적용, 실패 시 기존
  규칙 기반 mock으로 폴백

### 검증 — 얼굴 검출/마스킹 (요청하신 확인 사항)
합성 스크린샷(작은 얼굴 포함, SNS 게시물처럼 사진+캡션+시점 레이아웃) 8장 전부에서
**얼굴 검출 100% 성공** (신뢰도 49~57%, 이미지 폭 대비 약 11% 크기의 작은 얼굴도 잘
잡음). 마스킹 결과 이미지를 직접 눈으로 확인 — 얼굴만 검은 사각형으로 가려지고,
사진 밖에 있는 **캡션·게시시점 텍스트는 전혀 가려지지 않음**을 확인했다 (애초에
레이아웃상 사진 영역과 캡션/시점 텍스트 영역이 분리돼 있어 구조적으로 겹칠 일이
적음).

### 검증 — 패턴 탐지 정확도 (합성 스크린샷 기준)
| 테스트 세트 | 구성 | 결과 |
|---|---|---|
| 패턴 있음 (4장, 같은 놀이터·7일 간격) | "은행나무 놀이터", 2일전/9일전/16일전/23일전 | **"있음"** — 요일패턴(전부 일요일, 7일 간격), 장소반복, 캡션 내 정기방문 표현 3가지를 정확히 근거 게시물 번호와 함께 찾아냄 |
| 패턴 없음 (4장, 무작위 장소·불규칙 시간) | 할머니댁/집/해운대/서울대공원, 12시간전~3주전 무작위 | **"없음"** — 오탐 없이 정확히 판단, 근거 설명도 타당함("산발적으로 분포돼 반복 패턴 없음") |

두 세트 모두 원하는 대로 동작 — 오탐(false positive) 확인 완료.

### 처리 시간·비용 (실측)
- 스크린샷 1장 분석: 약 1.5~2초, 787 입력/75 출력 토큰 (약 $0.0012)

- 스크린샷 4장을 병렬 추출(약 4~4.4초) 후 패턴 분석(약 5초)이 순차로 이어져서, **스케줄
  분석 전체는 약 9.5초** — 이 구간은 병렬화해도 "추출 다 끝나야 패턴 분석 시작" 구조상
  더 줄이기 어려움
- 과거 게시물 스크린샷 4장 포함 시 **전체 진단 시간 약 17초** (메인 사진 처리 ~8초 +
  스케줄 분석 ~9.5초, 위험도진단/캡션제안과는 병렬) — 스크린샷 없을 때(약 9~11초)보다
  확실히 느려짐. 스크린샷 장수가 늘면 늘수록 패턴 분석 자체의 입력 토큰(게시물 목록)은
  늘지만 추출 단계는 병렬이라 크게 안 느려짐 — 병목은 "패턴 분석 1회 호출"의 고정 비용

## 12. 2단계 보정 — Canvas 기반 3종 (스마트 크롭 / 배경 흐림 / 스티커)

`아이사진_SNS위험진단_프롬프트.md` 3번(처리 방식 추천)까지 포함해서 구현. flux-kontext-pro
(fal.ai)는 이번엔 구조만 잡아두고 "준비 중"으로 표시.

### 큰 문제를 발견하고 방향을 바꾼 과정 (정직하게 기록)

원래 계획은 "Claude Vision이 준 위치(9분할)를 그대로 크롭/스티커에 쓴다"였는데,
**실제로 돌려보니 스티커가 텍스트를 완전히 빗나가는 심각한 문제**를 발견했다
(`test/correction-samples/text-only_sticker.png`의 초기 버전 — 별 스티커가 셔터/유리창
빈 공간에 찍히고 정작 간판 글자는 그대로 노출됨). 9분할을 고정 좌표(15/50/85%)로
매핑한 게 원인 — "상단"이라는 설명 자체는 맞아도, 사진 구도에 따라 실제 픽셀 위치는
15%가 아니라 25~40%일 수 있어서 근사치 수준을 넘어 완전히 빗나갔다.

**실험 1 — Claude Vision에게 숫자 bbox(%) 직접 요청**: 프롬프트를 바꿔 `{x,y,width,height}`
백분율을 요청하고 `꽃집간판.jpg`로 3회 호출, 각각 원본 이미지에 bbox를 그려서 눈으로
확인(`test/correction-samples/` 참고용 원본은 스크래치에만 있음). 결과: 호출당 7개 박스 중
1~2개만 실제 텍스트에 겹치고 나머지는 빈 공간에 찍힘 — 호출마다 어긋나는 정도도 들쭉날쭉.
"대략이라도 덮으면 채택" 기준에 못 미쳐서 **기각**.

**최종 채택 — 2단계 보정에서는 Tesseract 실제 bbox로 위치 재계산**: 1단계 진단의 텍스트
"내용"은 Claude Vision 결과를 그대로 쓰지만, 2단계 보정(크롭/스티커)에 들어갈 때는
`uploadedPhotoUrl`을 Tesseract로 한 번 더 돌려서 실제 픽셀 bbox를 구하고 그 위치만 사용함
(내용 판독 정확도는 Claude Vision보다 낮지만, 위치는 진짜 픽셀 데이터라 신뢰 가능).
추가 처리시간 1~2초 소요.

**알려진 한계 (사용자가 미리 지적한 부분, 실측으로 재확인)**: Tesseract는 `꽃집간판.jpg`에서
보통 1개 줄("교지 누아블룸" 등, 실행마다 인식 내용은 조금씩 다름)만 안정적으로 찾고,
전화번호·번지수는 여전히 못 찾는다. 즉 **크롭/스티커가 처리할 수 있는 건 Tesseract가
실제로 위치를 아는 텍스트뿐**이고, Claude Vision만 읽어낸(전화번호 등) 텍스트는 이번
보정에서 다루지 못한다 — 콘솔에 몇 개를 못 다뤘는지 로그로 남게 해뒀다.

### 구현 중 발견해서 고친 추가 버그 2개
- **스티커 크기 폭주**: 넓은 텍스트 줄(가로 900px+) 하나를 이모지 1개로 덮으려고
  `font-size = max(가로,세로)`로 잡았더니 화면 전체를 뒤덮는 거대한 별이 그려짐 →
  이모지를 텍스트 높이 기준 크기로 **가로 타일링**해서 해결
- **위치 재계산 레이스 컨디션**: 보정 화면 진입 시 Tesseract 재계산(1~2초)이 끝나기 전에
  사용자가 다른 방식 카드를 누르면 빈 위치 목록으로 처리되는 경우를 실측으로 확인 →
  계산 중엔 방식 카드를 비활성화하도록 수정

### 각 방식 실제 동작 확인 (`test/correction-samples/`)
3가지 테스트 사진(텍스트만/얼굴만/얼굴+텍스트) × 3가지 방식 = 9장 저장.
- **스마트 크롭**: 얼굴이 있으면 얼굴을 지키면서 텍스트 쪽 가장자리를 잘라냄
  (`face-plus-text_crop.png`). 얼굴이 없으면 화면 중심 근처 텍스트는 크롭만으로 못
  빼는 경우가 있고, 이땐 "스티커/흐림을 함께 쓰시겠어요?" 안내가 뜸 (요청하신 대로)
- **배경 흐림**: 얼굴 크기 기준으로 몸통~발끝까지 커버하는 영역을 추정해서 선명하게
  유지함. **전신 사진으로 별도 테스트**(`fullbody-original.png` → `fullbody-blur-result.png`)
  — 머리부터 신발까지 전부 선명하게 남고 배경만 자연스럽게 흐려지는 것 확인, 별도
  보정 불필요했음
- **스티커**: 텍스트 높이 기준 크기로 여유있게(세로 70%, 가로 30% 여유) 덮음. 여러
  스티커(🌟💫🎈⬛🔲) 중 선택 가능

### 처리 방식 추천 (프롬프트 3번)
보정 화면 진입 시 Claude에게 실제 위험요소 위치/유형을 주고 추천을 받아 1순위 배지를
동적으로 붙임. AI 배경교체는 아직 미지원이라 추천 후보에서 제외하도록 프롬프트에 명시.

### 다운로드 / 원본·처리본 비교
처리 결과를 PNG로 다운로드하는 버튼 추가(`canvas.toBlob` + `<a download>`). 미리보기는
원본(작은 썸네일) + 처리 후(큰 이미지) 나란히 표시.

### fal.ai flux-kontext-pro — 구조만 준비
`server/`에 `POST /api/replace-background` 스텁 추가(501 "준비 중" 응답). 프론트 카드에도
"준비 중" 배지 표시, 선택은 되지만 처리 없이 원본만 보여줌. 실제 연동은 팀원 fal.ai 키를
받은 뒤 진행 예정. → **13번 섹션에서 실제 연동 완료.**

### 회귀 테스트
1단계(OCR/얼굴분석/위험도진단/캡션제안/스케줄분석) 코드는 이번 단계에서 건드리지 않음.
`test/regression.js` 5케이스 전부 통과 확인.

## 13. fal.ai flux-kontext-pro 실제 연동 — 2단계 보정 2차

팀원분의 fal.ai API 키를 받아 `server/.env`의 `FAL_KEY`로 등록하고, 12번 섹션에서
스텁으로 남겨뒀던 `POST /api/replace-background`를 실제 fal.ai 호출로 교체했다.

### 구조
- 프론트 → 백엔드: 마스킹 없는 **원본** 이미지(base64) + 이미 알고 있는 텍스트 내용/유형/
  대략 위치 + 위험도 등급/장소 근거를 전달
- 백엔드: (1) 위 정보로 Claude Haiku에게 "이 사진에 맞는 flux-kontext-pro 편집 지시문(영어)"을
  생성시킴 → (2) `fal.storage.upload()`로 원본 이미지를 fal 스토리지에 업로드 → (3)
  `fal.subscribe('fal-ai/flux-pro/kontext', {prompt, image_url})` 호출 → (4) 결과 이미지를

## 14. 얼굴 검출 실패 시 프라이버시 안전장치 (긴급 수정)

13번 섹션의 실제 사진 검증 중, `flux검증.jpg`(거울 반사 셀카, 실제 인물 2명)를 1단계
진단에 넣었더니 **face-api.js가 인물을 전혀 감지하지 못했고(얼굴 0개)**, 코드를 보니
`maskFaces()`는 감지된 얼굴이 없으면 아무 것도 가리지 않고 원본을 그대로 반환하도록
되어 있었다. 즉 **"Claude Vision에 보내기 전엔 항상 얼굴을 마스킹한다"는 서비스의
핵심 프라이버시 원칙이, 얼굴 감지 자체가 실패하면 지켜지지 않는** 구멍이 있었음.
서비스의 핵심 주장과 직결된 문제라 최우선으로 바로 수정함.

### 검출 실패, 얼마나 흔한가 (실측)

face-only.png(정면 얼굴, 잘 검출됨)를 기준으로 흔한 실패 조건 5가지를 합성해서

| 조건 | 결과 |
|---|---|
| 정면 얼굴 (기준) | ✅ 검출됨 (신뢰도 77%) |
| **실제 사진 — 거울 반사 셀카 2인** | ❌ 0명 검출 |
| **작은 얼굴 (전체의 20% 크기)** | ❌ 0명 검출 |
| **기울어진 얼굴 (75도 회전)** | ❌ 0명 검출 |
| **눈 부분 가림 (선글라스 흉내)** | ❌ 0명 검출 |
| 저조도(어두운 사진) | ✅ 검출됨 (신뢰도 89%) |

**7개 중 4개(57%)에서 완전히 검출 실패** — 드문 예외가 아니라 실제로 자주 마주칠 수
있는 조건들(거울, 원거리, 기울어진 각도, 선글라스류)에서 뚫린다는 뜻.

**검증한 것과 안 한 것 구분**: 눈 부분 가림(선글라스류)은 검출 실패를 확인했지만,
**마스크 착용(코·입 가림)은 이번엔 검증하지 않음** — 얼굴 검출 실패 시 어차피 사용자
확인 절차(아래)를 거치므로 실패 조건을 전부 파악하는 것보다 안전장치 자체가 더
중요하다고 판단해 생략함. 필요하면 나중에 추가 검증 가능.

### 검토했지만 채택하지 않은 방법 — "전체 사진 흐림 처리 후 전송"

검출 실패 시 자동으로 사진 전체를 흐림 처리해서 보내는 방법을 먼저 검토했다.
`꽃집간판.jpg`(텍스트)와 `face-only.png`(얼굴)에 흐림 강도별로 실측:

| 흐림 강도 | 간판 텍스트 Tesseract 판독 결과 | 얼굴 식별 가능 여부 |
|---|---|---|
| blur(8px) | `"Bm ids"` (이미 의미 없는 글자로 깨짐) | 여전히 또렷이 식별 가능 |
| blur(16px) | (빈 문자열 — 아무 것도 인식 못함) | 이목구비는 흐려짐, 윤곽은 남음 |

**텍스트를 지킬 만큼 약하게 흐리면(8px) 얼굴이 안 가려지고, 얼굴을 가릴 만큼 강하게
흐리면(16px+) 텍스트가 이미 다 깨진다 — 그 사이의 절충점이 없어서 이 방법은 폐기.**

### 채택한 방법 — 얼굴 0개면 자동 전송을 멈추고 사용자에게 확인

얼굴이 1개 이상 감지되면 기존과 동일하게 자동으로 마스킹 후 전송한다(변경 없음).
**얼굴이 0개로 나오면, 그 즉시 아무것도 외부로 보내지 않고 먼저 확인 모달을 띄운다**:

- **[안전 우선 (전송 안 함)]** (기본 추천) — 메인 사진은 로컬 Tesseract만 사용(외부 전송
  전혀 없음, 정확도는 다소 낮아짐), 과거 게시물 스크린샷은 이번 스케줄 분석에서 제외
- **[그래도 원본으로 분석]** — 사용자가 "이 사진엔 실제로 사람이 없다"고 명시적으로
  판단했을 때만 선택 — 마스킹되지 않은 원본이 Claude Vision으로 전송됨

메인 사진(`runTextDetectionPipeline`)과 과거 게시물 스크린샷(`runScreenshotExtractionPipeline`)
양쪽 모두에 동일하게 적용. 한 번의 진단 동안(사진 1장 + 스크린샷 여러 장) 같은 선택을
재사용해서, 스크린샷마다 매번 모달이 뜨는 불편은 없앰. 콘솔에는 `[프라이버시]` 태그로
검출 실패/선택 결과를 항상 로그로 남김.

### 디버깅: 진짜 버그인 줄 알았던 curl 인코딩 문제

`/api/verify-correction`을 curl로 직접 테스트했을 때 Claude가 "모든 정보가 누락됨"이라고
반복 응답해서, 처음엔 Haiku의 신뢰성 문제(또는 프롬프트 버그)로 의심했다. 원인 추적 결과
(1) Anthropic API에 동일 프롬프트를 직접 호출하면 정상적으로 좋은 답이 나오는데, (2) 서버가
실제로 받은 `req.body`를 찍어보니 한글 키가 `"��������"`처럼 깨져서 도착하고 있었음 —
**Windows Git Bash에서 curl에 한글을 직접 넘길 때 생기는 인코딩 문제**였고, 서버 코드
자체는 문제없었다. 실제 브라우저는 `fetch`+`JSON.stringify`로 보내기 때문에 이 문제와
무관함을 확인. (교훈: 비-ASCII payload는 curl보다 실제 브라우저/Playwright로 검증할 것.)
