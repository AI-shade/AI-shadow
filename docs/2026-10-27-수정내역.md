## 2. 항목별 상세

### A. 슈퍼베이스 연결

- **목적**(사용자): 사진을 유형(실내/기관 앞/거리/단체/클로즈업 …)으로 나눠, 유형마다 분석법을 달리해 효율과 정확도를
  높이려는 것. 슈퍼베이스는 그 분석법을 재고 비교할 **개발용 정답셋**을 담는다. 서비스 사용자 사진은 저장하지 않는다.
- **한 것**: 슈퍼베이스 프로젝트 생성(사용자가 대시보드에서 직접 — Claude의 생성 요청은 권한 검사에서 막힘), 연결 확인.
  - 저장소: `server/.env.example`에 `SUPABASE_URL`, `SUPABASE_SECRET_KEY` 칸 추가(값 비움)
  - 새 파일 `scripts/supabase-check.mjs`: `server/.env`를 직접 읽어 `/storage/v1/bucket`을 부르고 버킷 목록만 출력.
    키는 출력하지 않는다. 새 키(`sb_secret_…`)는 `apikey` 헤더만, 옛 service_role(JWT)은 `Authorization`도 보낸다.
  - 실행: `node scripts/supabase-check.mjs` → `연결됨: eercjqzhtydhqtgmgqla.supabase.co / 버킷 0개`
- **결정 보류**(사용자가 "기다려"): 표(`photos`, `runs`)·Private 버킷 생성, 사진 103장 업로드(팀이 출처·동의 확인 후),
  사진 유형 기준 합의. 사진은 `CNUtest2/사진 100장 분석/`에 103장, 508MB(무료 1GB 안).
- **사고**: 원인 조사 중 `.env`를 «키 값은 가리고 이름만» 보여주는 명령이 `=`만 찾게 짜여 있었는데, 사용자가 `:`로 적은
  줄을 못 가려서 **비밀 키가 대화에 찍혔다.** 사용자가 대시보드에서 새 키 발급 → 옛 키 삭제 → `.env` 교체. 새 키로 연결 재확인.

- **문제**: `GOOGLE_VISION_API_KEY`, `CNU_LLM_API_KEY`, `KAKAO_REST_API_KEY`가 두 번씩 있었고 아래쪽은 빈 값.

- 형식도 고침: `SUPABASE_URL:https://…/rest/v1/` → `SUPABASE_URL=https://….supabase.co`, `SUPABASE_SECRET_KEY: …` → `=…`.

### C. 누운 사진 — 사용자가 직접 돌리기

- **제보**(`옷바꾸기 버그 보고서.pdf`, 실제로는 배경 교체 버그):
  > "왼쪽 사진을 배경변경했는데 지 맘대로 옷도바꾸고 사진 방향이 바꼇다고 인식을 못하고 배경도 세로기준로 바꿔버렸어 이상하게"
- **잰 것**:
  - 예시 사진 2장을 90° 돌리면 — 태권도복: 진짜 얼굴은 놓치고 **문의 로고를 얼굴로** 잡음, 인물 분리는 **다리 끝·바지 일부를 놓침**.
    원복: 얼굴 0명. → 보고서 그대로: 상체는 원본으로 되돌아왔고, 놓친 다리에 AI가 그린 청바지가 남았다.
  - **자동 방향 판단을 재봄**(`docs/실험/rotate-scores.js`): 바른 방향 사진 25장을 0/90/180/270°로 돌려 얼굴 신뢰도 비교.
    신뢰도 합 기준 18/25, 최고 신뢰도 기준 20/25만 0°를 고름. 얼굴 검출기는 거꾸로 돌린 사진에서도 신뢰도 0.8짜리
    "얼굴"을 자주 찾는다 → **5장 중 1장꼴로 멀쩡한 사진을 눕힌다. 그래서 자동 판단은 하지 않기로**(사용자 결정: "ai가 하지말고").

  - `rotatePhoto90(url)`: 시계방향 90° 돌린 JPEG(0.95) object URL을 돌려줌. 누를 때마다 `uploadedPhotoUrl`을 바꾼다.
  - `originalPhotoUrl` 새 변수: 올린 파일 그대로. `ensureExifRead`가 `originalPhotoUrl || uploadedPhotoUrl`에서 읽는다
    (캔버스를 거치면 EXIF 좌표가 사라지므로). 새 파일을 올리면 `lastExifResult = null`.
  - `noFaceConsentModal`에 안내 한 줄: 누워 있으면 «안전 우선» → ↻ 돌리기 → 다시 진단.
  - 테스트 훅: `uploadedPhotoUrlForTest`, `originalPhotoUrlForTest`, `rotatePhoto90`. `setPastCountForTest`도 `originalPhotoUrl` 설정.

### E. 배경 교체 — kontext → fill + 사람 마스크

- **원인**: `fal-ai/flux-pro/kontext`는 사진 **전체**를 다시 그린다. 인물 보호는 프롬프트의 "do not modify the person"뿐
  (서버 주석에도 "픽셀 단위 보장이 없음"). 그 뒤 인물 분리로 원본 사람을 덮어씌웠지만, 누운 사진에서 인물 분리가 다리를
  놓치자 AI가 그린 청바지가 남았다. AGENTS.md «부탁이 아니라 차단» 원칙이 이 기능에만 빠져 있었다.
- **방식**: 옷 교체와 같은 `fal-ai/flux-pro/v1/fill`. 마스크 흰색 = 사람 바깥 전부(다시 그림), 검정 = 사람(보존).
- **프론트**(`index.html`):
  - `BG_FAL_MAX_SIDE = 1024`, `falSendSize(ow, oh, maxSide)`(세 번째 인자 없으면 1568). 1024×768 = $0.039(kontext $0.04와 같음).
    사용자 결정: "바꿀 방식 (fill), 긴 변 1024px로 줄여 보냄 — 테스트는 내가할게".
  - `buildBackgroundMask(faceBoxes, imgW, imgH, personMask, handBoxes)`:
    1) 흰 바탕 2) 인물 분리를 `max(3, 짧은 변×1.2%)`px 넓혀 **알파가 조금이라도 있으면** 검정 3) 마지막에 얼굴·손 상자를 검정.
    - 얼굴·손 상자는 **인물 분리와 15% 이상 겹치는 것만**, **여백 없이**, **바깥쪽 정수 픽셀로** 칠한다.
      처음엔 옷 마스크처럼 얼굴 상자를 넉넉히(위 55%·옆 35%) 넓혔는데, 마스크를 얹어 보니 **얼굴 옆 «햇살언…» 간판이 원본
      그대로 남았고, 배경 포스터 속 아이 얼굴까지 네모로 보존**됐다. 소수점 좌표로 칠하면 손 상자 테두리 2px이 열렸다.
  - `runBackgroundFill(img, faces, riskResult, ocrResult)`: `getPersonMask`가 null이면 `err.noPerson`으로 **보내지 않고 멈춤**
    (kontext로 돌아가지 않는다). 1024로 줄인 사진·마스크를 만들고 `/api/replace-background`에 보낸 뒤
    `compositeThroughMask`로 배경 자리에만 합성(사람은 원본 해상도 그대로).
    - `imageBase64` = 마스크 안쪽(옛 배경)을 **회색으로 지운** 사진(`blankInsideMask`) — 옛 간판 구조를 베끼지 않게.
      **배경에서는 A/B로 재보지 않았다**(옷 교체에서 확인된 근거를 옮김).
    - `contextImageBase64` = 지우지 않은 같은 크기 사진 — 서버에서 Claude가 장소를 정하는 데만 쓴다(회색만 보면 실내/실외를 모른다).
  - `selectMethod`의 `method === 'ai'` 블록: kontext 후처리(비율 가드·`removeHallucinatedPeople`·`matchFaces` 정렬·
    `restorePersonFromOriginal`)를 지우고 `runBackgroundFill` 결과를 씀. `runFluxBackgroundReplace` 함수 삭제.
  - 테스트 훅: `runBackgroundFill`, `buildBackgroundMask`, `falSendSize`.
- **서버**(`server/server.js`):
  - `FLUX_PROMPT_SYSTEM`: «kontext 편집 지시» → «FLUX Fill: 사람은 마스크로 보호, 배경 전체를 무엇으로 채울지 묘사».
    인물 묘사 금지·구체적 일반 장소 규칙 유지, `no text, no letters, no signage, no logos, no other people` 필수, 조명 맞추기.
  - `/api/replace-background`: **`maskBase64` 없으면 400**(Claude·fal 부르기 전에). `generateFluxPrompt`에는
    `contextImageBase64 || imageBase64`. `fal-ai/flux-pro/v1/fill`(`safety_tolerance '4'`, `output_format 'png'`, 시드·3회 재시도는
    `/api/inpaint-regions`와 동일), 비용 `estimateFillCostUsd(w,h) × attempts`. kontext 호출 코드 삭제.
- **테스트**: 새 `test/background-mask.js` 22/22(얼굴·손·사람 0픽셀 열림, 간판·포스터 얼굴은 열림, 크기, 사람 없으면 멈춤),
  새 `test/bg-endpoint.js` 3/3(마스크·이미지 없으면 400, Claude·fal 안 부름). `test/background-replace-live.js`(유료)는
  새 경로로 고치고 «사람 픽셀이 원본 그대로» 검사 추가 — **돌리지 않음**.
- **사고**: `bg-endpoint.js`를 처음 돌릴 때 **고치기 전 서버가 3001에 남아 있어** 마스크 없는 요청이 통과, **Claude가 1회 실제로
  불렸다**(1×1 이미지라 "볼 수 없다"고 답해 fal까지는 안 감, 몇 원). 서버 재시작 후 통과. 테스트 머리에 경고를 적어 둠.
- **사용자 테스트 결과**(`옷.배경교체 결과보고서.pdf`): 1쪽 아래(가을 호수) — 사람 그대로, 배경만 자연스럽게 바뀜 ✓.

### F. 옷 교체 — 옷 전체 하나, 원래와 비슷한 차분한 색

- 사용자 결정: 옷 교체 선택지는 «하나만 (옷 전체)». 색은 "너무 극단적으로 바뀌지만 않았으면".
- **한 것**(`index.html`):
  - `selectMethod`의 `outfit` 블록을 새로 씀: 진단 확인 → `checkFluxStatus` → **늘 `askFluxConsent`** → 얼굴 없으면 안내
    (누운 사진이면 돌리라고) → `runOutfitSwap(img, faces, risk, 'keep', 'none')`. 색만 바꾸기(로컬)·마크만 지우기 분기 삭제.
  - `outfitColorPhrase(p, crew, shift)`: `shift`면 `in a slightly different, more muted shade close to <색>`.
    `buildOutfitFillPrompt`의 `keepColors && colors` 분기가 `shift=true`로 부름. 여러 명이면 `Each person wears colors close to their own…`.
    부정문·«original» 낱말은 쓰지 않는다(기존 테스트 규칙: 적으면 그 물체를 불러온다).

### G. 옷 자리를 회색 대신 «옷끼리만 흐린 원본»으로

- **사용자 테스트**(`옷.배경교체 결과보고서.pdf` 1쪽 위, 옷 교체): 얼굴·배경은 원본 그대로인데 **얼굴 아래 몸 전체가 새로 그려짐**
  — 패딩→얇은 니트, 베이지 바지→흰 바지, 더 마른 체격, 없던 운동화·자세, 몸 옆 네모 얼룩.
- **잰 것**: 그 사진에 옷 마스크를 얹어 보니 목도리+패딩+바지 = **목 아래 몸 전체**(사진의 10.8%), 손은 주머니 속이라 검출 0,
  바위 일부도 옷으로 잡힘. 옷 교체는 그 자리를 **회색으로 지워** 보낸다(`OUTFIT_BLANK_INSIDE_MASK = true`, 예전 A/B: 원본을
  보내면 흰 깃·리본·허리띠 같은 헌 옷 조각이 섞임). 옷이 몸 전체를 덮으면 AI는 회색 사람 모양만 보고 몸을 새로 지어낸다.
  (사용자 질문 "얼굴만 마스킹 하는거 아니였어?" — 얼굴 보호(검정)는 정상이었고, 문제는 «다시 그릴 곳»인 옷이 몸 전체였던 것.)
- **세기 정하기**(`docs/실험/blur-levels.js`): 1% / 2% / 3.5%를 사진 3장(패딩 아이, 교복 학생, 태권도복)에 얹어 비교.
  - 1%: 로고가 아직 보임(KOREA 패치, 교복 엠블럼 흰 점)
  - 2%: 엠블럼은 사라지나 **태권도복 빨간 V 칼라·검은 띠가 색 띠로 남음** → 헌 옷 조각이 되살아날 위험
  - **3.5%**: 마크·배색 사라짐, 몸 윤곽·대표 색 유지 → 채택
- **한 것**(`index.html`): `OUTFIT_BLUR_RATIO = 0.035`, `blurInsideMask(ic, mask, sw, sh)`. 옷 픽셀만 남긴 층(`maskToAlpha`로
  `destination-in`)을 `blur(짧은 변×3.5%)` — 캔버스가 알파를 곱한 채 흐리므로 배경·살색이 옷 자리로 번지지 않는다. 알파를
  채운 뒤 다시 마스크 알파로 잘라 원본 위에 얹음. `runOutfitSwap`에서 `blankInsideMask` 대신 `blurInsideMask`
  (`blankInsideMask`는 배경 교체가 계속 씀). `OUTFIT_BLANK_INSIDE_MASK` 주석 갱신.
- **결과**: 앱이 실제로 보내는 사진을 가로채 확인 — 회색 사람 모양 대신 «검은 패딩 + 밝은 바지» 덩어리가 보인다.
  `outfit-blank.js`(고침) 12/12: 줄무늬의 빨강 채널 퍼짐 95 → 13(예측 ≈14), 대표 색 `[126,94,45]`(무늬 평균 ≈125,95,45).
- **아직 모름**: 실제 AI 결과(체형 유지·헌 옷 조각 섞임 여부) — 사용자가 직접 테스트하기로.

### H. 하의 색 오독 (긴 패딩)

- **발견**: G를 확인하며 가로챈 프롬프트가 베이지 바지에 `trousers … close to black`을 지시하고 있었다.
- **원인**: `describeOutfitColors`는 하의를 «어깨 아래 얼굴 높이 2.4~3.6배» 띠의 중앙값으로 읽는다(어린이 몸 비율 가정).
  긴 패딩이 띠 위쪽 절반을 덮어 중앙값이 패딩 색이 됐다.

  남은 게 띠 안 옷의 25% 미만이면 상하의 같은 색으로 보고 전체 중앙값. 하의 호출에 `top`을 넘김.
- **결과**: 합성 사진 «긴 검은 패딩 + 베이지 바지» → bottom `beige`(전: `black`), «남색 상하의» → `navy` 그대로.

## 6. 남은 일·결정 사항

1. **사용자 테스트 필요**: G(흐림 3.5%)로 패딩 아이 옷 교체 — 체형 유지, 바지가 검정이 안 되는지, 헌 옷 조각이 안 섞이는지.
2. **배경 교체 프롬프트**: «원래와 다른 종류의 장소로» 한 줄(야경이 야경으로 나옴) — 미반영.
3. **옷 교체 기본값을 «로고만 지우기»로**(사용자 확정 방향) — 설계 미착수. 재료: I의 로고 찾기 + 구글 비전 글자 상자 + 브러시.
4. **커밋 안 함**. 팀원 코드와 맞추는 일은 사용자가 «안 해도 괜찮아».
5. 정리할 것: 화면에서 빠진 방식의 내부 함수·테스트, 보정 화면 진입 때 아직 도는 글자 위치 재계산(구글 비전·Tesseract) —
   새 두 방식은 쓰지 않는다.
6. 슈퍼베이스: 표·버킷·사진 유형 기준·업로드·삭제 시점 — 사용자 결정 대기.
